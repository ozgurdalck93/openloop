# OPENLOOP — Differentiation Roadmap

## v0.1 — Prove the loop model

Goal:
Prove users understand and value:
“the app remembers unresolved things for me.”

Build:
- capture
- classification
- review
- waiting loops
- notifications
- transitions
- context resurfacing

## v0.2 — Context memory

Add:
- images
- screenshots
- links
- voice notes
- contextual attachments

Example:
“Bring this jacket back after payday.”
When resurfaced:
show image + note:
“M fit better than XS.”

## v0.3 — Promise & Waiting intelligence

Add dedicated intelligence for:
- things I promised,
- things people promised me,
- expected replies,
- refunds,
- applications,
- deliveries,
- approvals.

Home insight:
“3 things are currently waiting on other people.”

## v0.4 — Future-self packets

User can leave:
- decision,
- reason,
- evidence,
- attachments,
- condition for resurfacing.

Example:
“Don’t buy XS. M looked better.”
Bring the reason back with the item.

## v0.5 — Screenshot inbox

User shares screenshot to OPENLOOP.

System detects:
- product to revisit,
- event,
- booking,
- address,
- deadline,
- promise in a message,
- document,
- price,
- follow-up.

Important:
Screenshot understanding should feed the same Loop Engine.
Do not build a separate screenshot-task system.

## v0.6 — Communication follow-up

With explicit user permission:
- Gmail / Outlook integrations
- detect sent messages awaiting reply
- suggest waiting loops
- never send autonomously without user action

## v0.7 — Smart timing

Learn patterns such as:
- errands: afternoon / leaving-home window
- calls: business hours
- personal follow-ups: evening
- admin: weekday mornings

User remains in control.

## v0.8 — Life workflows

Reusable inferred workflows:

### Return
return item
→ wait for merchant receipt
→ wait for refund
→ resolve

### Application
submit
→ wait for response
→ follow up
→ interview/event
→ decision

### Medical/admin result
appointment/test
→ result date
→ check result
→ next action

### Purchase consideration
save
→ revisit later
→ compare
→ decide
→ resolve

The user should not manually configure these as automation rules.
The system proposes them from context.

## Long-term moat

The moat is not “we use AI”.

It is:
1. a personal graph of unresolved life states,
2. reliable state transitions,
3. remembered context and reasons,
4. increasingly accurate resurfacing timing,
5. cross-source continuity.

The product should eventually feel like:
**“I can safely stop keeping this in my head.”**
